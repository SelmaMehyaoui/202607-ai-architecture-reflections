Executive summary

Three paths. One correct result.

Every measured invocation succeeded and produced the same semantic output. The consequential differences were startup behavior, steady-state overhead, and the authority available behind the invocation.

!
The latency result is about lifecycle design, not MCP in the abstract.

The skill benchmark starts a new Python interpreter for every observation. Warm MCP calls reuse a persistent server session. That makes steady-state MCP much faster here, while the skill remains the fastest cold path.

Hypothesis review

What this run supports - and what it cannot settle.

These verdicts apply only to this implementation, lifecycle, host, and configuration. “Supported” means consistent with the observations, not proven universally.

H1

Qualitatively observed

Responsible reading

Observed fact is not architectural law.

Observed on this Mac

  • All three wrappers returned the correct deterministic summary.
  • Persistent MCP sessions were faster for warm calls than process-per-call skill execution.
  • The isolated configuration could not see unmounted host files or the dummy host environment variable.
  • The isolated root filesystem prevented an unrelated write.
  • The isolated process could still spawn a subprocess and read container system files.

Qualified interpretation

  • Persistent service lifecycle can dominate tiny-task invocation performance.
  • A local MCP process can improve interface standardization without reducing OS-user authority.
  • A separately configured container can narrow filesystem, environment, and network reach.
  • Security came from the actual boundary and least-privilege settings - not from the word “MCP.”
  • Primitive capability inside a container is different from access to host resources.

Limitations and next steps

Useful evidence, not a universal benchmark.

  1. One host and one run date. Results need repetition across machines and runtime versions.
  2. One cold observation. Cold-start comparisons are descriptive and especially sensitive to caches and runtime state.
  3. Unequal warm lifecycle. MCP reused a server session; the skill restarted Python. A persistent skill worker or process-per-call MCP condition would isolate lifecycle effects.
  4. Tiny computation. The task intentionally magnifies orchestration overhead; heavier workloads will change the proportions.
  5. Host probes approximate OS authority. They were not exposed as actual skill or MCP tools and therefore do not measure semantic tool reach.
  6. Resource usage incomplete. CPU time, peak memory, process count, and filesystem I/O were not captured consistently.
  7. Host network probe inconclusive. DNS failure against an invalid domain does not establish a network policy.
  8. No model-selection variability. The harness intentionally excludes an LLM so architecture overhead is measured independently.
